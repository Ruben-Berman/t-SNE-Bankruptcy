● The bug is where return p_j_given_i sits. It's indented at the same level as
  the if i != j: line, so Python treats it as part of the inner for j loop.
  Here's what happens when you call the function:

  1. i = 0, j = 0 → i != j is False, so the if block is skipped.

  with.

> this is taking still way too long, can we incorporate paraellisation in here?
  What else can be done to speed this up

● Parallelising won't fix this. Vectorising will. Almost all the time goes on
  Python-level .iloc calls. With ~850 rows (6,819 ÷ 8), that's about 720,000
  iterations, each pulling two rows out of pandas. Splitting that across 4–8
  cores would only make it 4–8× faster. NumPy can compute every pairwise
  distance in one call, which is thousands of times faster and runs in
  milliseconds.

  There's also a bug in your current version: Denominator = 0 is set once,
  before the for i loop. So it adds up the numerators for all rows, and you're
  dividing by a single total across the whole matrix. For p_{j|i}, each row
  needs its own denominator, which means each row of the result should sum to 1.

  Here's a vectorised replacement that fixes both problems:

  from scipy.spatial.distance import pdist, squareform

  def TSNE_ALGO(Xvarqt, PERPLEX, ETA):
      X = Xvarqt.to_numpy() #Plain NumPy array: no pandas overhead
      #All pairwise Euclidean distances at once (n x n matrix)
      Distance = squareform(pdist(X, metric='euclidean'))
      Numerator = np.exp(-Distance**2 / (2 * PERPLEX**2))
      np.fill_diagonal(Numerator, 0) #Exclude k = i
      #Row-wise denominator: one sum per point i
      Denominator = Numerator.sum(axis=1, keepdims=True)
      p_j_given_i = Numerator / Denominator
      return p_j_given_i

  Mapping it to your loops:

  - pdist + squareform is your Distance[i, j] loop, run in compiled C.
  - np.exp(...) on the whole matrix is your Numerator[i, j] loop.
  - fill_diagonal(..., 0) replaces the if i != j check.
  - .sum(axis=1, keepdims=True) gives one denominator per row, shaped (n, 1) so
    it broadcasts across the columns.

  Check it with:

  P = TSNE_ALGO(Random_Xvarqt, PERPLEX, ETA)
  print(P.shape, P.sum(axis=1)[:5]) #each row should sum to 1

  Other ways to speed things up as you build out the full algorithm:

  - Keep everything in NumPy. Call to_numpy() once at the start. The
    gradient-descent loop will run hundreds of iterations, so it must not touch
    .iloc.
  - When you add the σᵢ binary search, loop over i but vectorise over j, working
    on the whole row Distance[i, :] at once. That's about 850 cheap iterations,
    which is fine.
  - If you really do need parallel loops, numba with @njit(parallel=True) and
    prange is the simplest route. You won't need it for n ≈ 850.
  - The full dataset is fine too: at n = 6,819 the n × n matrix is about 370 MB
    in float64. Use .astype(np.float32) to halve that if memory gets tight.

  Numba compiles your loops to machine code. That's also how you get
  parallelisation without changing how the code reads:

  from numba import njit, prange   # pip install numba

  @njit(parallel=True)
  def TSNE_LOOPS(X, PERPLEX):
      n = X.shape[0]
      p_j_given_i = np.zeros((n, n))
      for i in prange(n): #prange = rows i are split across CPU cores
          Numerator = np.zeros(n)
          Denominator = 0.0
          for j in range(n):
              if i != j:
                  dist_sq = 0.0
                  for d in range(X.shape[1]): #Squared Euclidean distance,
  element by element
                      dist_sq += (X[i, d] - X[j, d])**2
                  Numerator[j] = np.exp(-dist_sq / (2 * PERPLEX**2))
                  Denominator += Numerator[j]
          for j in range(n):
              if i != j:
                  p_j_given_i[i, j] = Numerator[j] / Denominator
      return p_j_given_i

  P = TSNE_LOOPS(Random_Xvarqt.to_numpy(), PERPLEX)

> I think if I just keep the P matrix on it's own loops without combining it,
  and just take that for the final loop with the KLD and Q it'll be fine right?

● Yes. P depends only on the high-dimensional data, so it never changes during
  the optimisation. Compute it once with its own loops, before the
  gradient-descent loop, and only Q and the gradient get recomputed on each
  iteration. That's how t-SNE is meant to be structured.

  There's one step to add before you pass P into the KL/gradient loop.

  Make P symmetric. t-SNE doesn't use the conditional p_{j|i} directly. It uses
  the joint probability

  $$p_{ij} = \frac{p_{j|i} + p_{i|j}}{2n}$$

  As a loop:

  n = len(p_j_given_i)
  P = np.zeros((n, n))
  for i in range(n):
      for j in range(n):
          P[i, j] = (p_j_given_i[i, j] + p_j_given_i[j, i]) / (2 * n)

  Every entry of P now adds up to 1 across the whole matrix, not one row at a
  time. Q is built the same way, normalised over all pairs, so the KL divergence
  compares two distributions on equal terms. Without this step, KL(P‖Q) and the
  gradient formula 4 Σⱼ (pᵢⱼ − qᵢⱼ)(yᵢ − yⱼ)(1 + ‖yᵢ − yⱼ‖²)⁻¹ won't be
  correct.

  Your structure should look like this:

  1. p_j_given_i   ← loops (once)
  2. P (symmetric) ← loops (once)
  3. Y ← small random init, e.g. rng.normal(0, 1e-4, (n, 2))
  4. for t in range(T):
         Q        ← loops over Y (every iteration)
         gradient ← loops using P, Q, Y
         Y        ← update with ETA (+ momentum)
         KLD      ← optional, e.g. every 50 iterations to monitor

  Two things to keep in mind:

  - Speed: step 4 is the part that runs hundreds of times. If anything gets the
    Numba treatment, it should be the Q and gradient loops, not P.
  - Perplexity: P still uses PERPLEX directly as σ. That works, but it isn't
    proper t-SNE until each σᵢ is found by binary search to match the target
    perplexity. Since that only changes how P is built, you can add it later
    without touching anything in the loop.

  What's new here:
  - sns.JointGrid: it gives you the main plot (g.ax_joint) plus a histogram
    panel along the top (g.ax_marg_x) and one down the side (g.ax_marg_y). Each
    histogram lines up with its own axis.
  - stat='density', common_norm=False: this is essential. Only about 3% of the
    companies are bankrupt, so on raw counts the red histogram would be a flat
    line. With these settings each class is scaled on its own, so you can
    compare their shapes. For example, you can see whether bankrupt firms bunch
    up at one end of Component 1.
  - Contours instead of points: kdeplot replaces the thousands of faded blue
    dots with filled density shapes, one colour per cluster. Contours suit this
    plot because the background becomes clean shapes and the red points stand
    out much more. Only the non-bankrupt points are contoured; the bankrupt ones
    are left as individual points so you can still see each one.

  - A still 3D image is hard to read. Points in front hide the ones behind, and

● The KNN imputation is in Berman_Patel_code.py:154-189
  (Berman_Patel_code.py#L154-L189). Step by step:

  1. Which variables were imputed (line 171)
  Variables with 1.5% to 50% corrupted values (≥ 1000) were selected. Above 50%
  there were too many to fill in, so those variables were turned into binary
  flags instead (lines 139–143). Below 1.5% there were few enough to winsorise

  2. Marking the corrupted values as missing (line 174)
  In those 7 variables, every value above 1 was replaced with NaN. The imputer
  only fills NaNs.

  3. Choosing which variables to compare companies on (lines 176–183)
  - Correlations: Spearman correlations were recomputed with the corrupted
    values removed.
  - Clean candidates: only variables with no corrupted values at all could be
    used to judge similarity (clean_vars), so the comparison isn't distorted by
    corrupted numbers.
  - Picking the four: for each variable being imputed, the 4 clean variables
    most strongly correlated with it were chosen, by absolute Spearman
    correlation. Which four these were is printed for each variable (line 185).

  4. Imputing (lines 160 and 187–189)
  KNNImputer(n_neighbors=5) was run on just 5 columns: the variable itself plus
  its 4 chosen variables.
  - Finding similar companies: for a company with a missing value, the imputer
    finds the 5 companies most similar to it, measured by Euclidean distance on
    the 4 chosen variables.
  - Filling the gap: the missing value is replaced with the average of those 5
    companies' genuine values.
  - Keeping the result: only column 0, the imputed variable, is written back.
    The 4 comparison variables are left unchanged.

  Why it was done this way: choosing the comparison variables separately for
  each imputed variable means companies are matched on the ratios that actually
  relate to the missing one. All variables are already on a 0–1 scale, so no
  extra scaling was needed before measuring distances.

  - Lines 162–167: the note lists Research and development expense rate at

    output from an earlier version, so it's best to update or delete it before

  #Rows flagged by all three models

  The last line is the evidence for your story. If a large share of the flagged
  rows contain values ≥ 1000, then the models were mainly picking up corrupted
  entries, not unusual companies. That justifies the counting, flagging, KNN
  imputation and winsorising that follow. Put the printed number in the report.

  2. On the cleaned data (Xvarqt), in the #OUTLIER DETECTION placeholder

  Yes, feed it Xvarqt there. It's the same data your t-SNE uses, so you can draw
  the flagged rows on the t-SNE map. Run the same code again with Xvarqt
  instead of Xvar, and name the result anomalies_clean.

  Using Xvarqt rather than Xvar_reduced makes almost no difference to the
  results. ECOD and COPOD only look at the order of values within each variable,
  which the quantile transform doesn't change. Isolation Forest changes
  slightly. So choose Xvarqt because it matches your t-SNE input, not because it
  changes the result.
